# Native Codex CLI Provider Design

## Goal

Allow Myference to serve text generated by the Codex CLI already installed and authenticated on a provider machine. Native Codex uses the machine's ChatGPT-managed Codex login, requires neither an OpenAI API key nor Docker, and exposes only final model text and metered usage to marketplace clients.

## Provider ownership

`backend add --kind codex --name <offer> --model <model>` selects the native runner when no image is supplied. The existing digest-pinned Docker agent remains available when both `--image` and `--secret` are explicitly supplied. OpenAI, Ollama, Claude, and Kimi behavior is unchanged.

An explicit replacement option can migrate an existing backend with the same name. This keeps the public offer ID, model, price version, and marketplace history stable while changing only its local execution backend. Replacing an OpenAI backend with native Codex removes the now-unused credential entry for that backend name after configuration is saved successfully.

## Native execution boundary

Each generation runs the host's resolved `codex` executable with `exec`, `--ephemeral`, `--json`, `--ignore-rules`, `--sandbox read-only`, `--skip-git-repo-check`, the configured model, and stdin prompt input. The process receives a minimal environment and an empty per-job working directory. Workspace files are rejected rather than materialized.

Myference maintains a private Codex provider home under its local application state. It seeds that home once from the user's existing Codex `auth.json`, then lets Codex update the private copy so OAuth refresh-token rotation remains consistent. `USERPROFILE`, `HOME`, and `CODEX_HOME` point at that private home, preventing discovery of the user's normal configuration, plugins, MCP servers, apps, rules, and global skills.

The provider config disables web search and multi-agent behavior and enables a trusted `PreToolUse` hook. The hook denies every supported local tool before execution and records a per-job marker. The runner also rejects JSON events representing command execution, file changes, MCP calls, web searches, or other tools. If a tool is attempted, the request fails and no tool diagnostic or generated text is sent to the client.

Codex documents hooks as a guardrail rather than a universal security boundary. Myference therefore combines the hook with an empty read-only workspace, isolated home, disabled hosted tools, minimal environment, JSON event rejection, and no workspace input. The provider never promises general Codex agent execution; its supported contract is text-only generation.

## Output and accounting

The runner buffers `agent_message` text until `turn.completed`, reads Codex's reported `input_tokens` and `output_tokens`, verifies the output token reservation, and then emits only the final text. It reports wall-clock compute milliseconds through the existing provider accounting contract. Missing completion, missing usage, empty output, over-limit usage, nonzero exit, timeout, or any tool attempt makes the backend unhealthy with a diagnostic retained locally.

Codex CLI does not expose a strict upstream maximum-output-token flag. Myference supplies the requested limit as provider instructions, buffers output, and refuses output whose reported usage exceeds the reservation. This prevents unreserved output from reaching or billing the marketplace client, although the provider's own Codex account may still consume the attempted generation.

## Installation and diagnostics

The public Myference installer remains responsible only for Myference artifacts. Native Codex discovery requires `codex` on `PATH` and a readable existing Codex login; errors instruct the provider to install/login to Codex. `myference capacity` and provider status report native Codex unavailable when either prerequisite is missing.

## Verification

Unit tests cover command construction, isolated environment, provider-home initialization, deny-hook output, JSON parsing, tool-event rejection, output buffering, usage accounting, timeouts, and replacement semantics. A live Windows acceptance test migrates the existing `gpt-5.3-codex` offer, executes a harmless text-only prompt, verifies token usage and no tool marker, then confirms the normal Scheduled Task remains connected with one process and all offers healthy.
